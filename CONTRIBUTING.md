# Contributing to SharpCompute

Thanks for your interest. SharpCompute is in early development with a single maintainer, so issues,
bug reports with a small reproducing shader, and focused pull requests are all welcome. For a large
change, open an issue first so the design can be agreed before you write the code.

By taking part you agree to the [Code of Conduct](CODE_OF_CONDUCT.md). Security problems go through
the [security policy](SECURITY.md), not public issues.

## Requirements

- macOS 15 or later on Apple Silicon (the only backend today is Metal).
- The .NET SDK that [`global.json`](global.json) names (.NET 11).
- Optional: the Xcode Metal Toolchain, to precompile shaders at build time; without it they are
  compiled at run time and the tests that need a precompiled library are skipped.
- Optional, for screenshots and GIFs: `ffmpeg` (and `pngquant`), from Homebrew.

## Build and test

```sh
dotnet build SharpCompute.slnx
dotnet test SharpCompute.slnx
```

- The build treats warnings as errors (`TreatWarningsAsErrors`): a pull request builds with
  0 warnings.
- `-p:SharpComputePrecompileShaders=false` builds and tests everything without precompiled shaders.
- The vector, matrix and intrinsic sources are generated by `tools/gen_vectors.py`. Change the
  generator rather than its output, and check with `python3 -I tools/gen_vectors.py --check`.
- Run one area with a filter while you work, for example `dotnet test SharpCompute.slnx --filter ReadmeImage`,
  and the full suite before you open the pull request.

There is no CI: the full test suite run locally is the check, so say in the pull request that it
passed.

## Code style

Match the code around your change:

- File-scoped namespaces, nullable enabled, explicit `using` directives (implicit usings are off).
- XML doc comments on public APIs that explain *why* and state thread-safety, not just restate the
  signature.
- Interop is AOT-safe: `LibraryImport` and `objc_msgSend`, `[UnmanagedCallersOnly]` callbacks, no
  reflection. Native objects are held the way the runtime already holds them (handle leases,
  autorelease pools).
- New sample source files start with `// Original SharpCompute sample (MIT).`

## Tests

- Every public API gets tests, edge cases included.
- A shader feature is tested on the GPU and with `ForCpu`, and the two results are compared:
  `ForCpu` is the reference the GPU result is held to. GPU tests use `[MetalFact]` or
  `[MetalTheory]`, so they are skipped, not failed, on a machine without a Metal device.
- Generator changes get tests in `tests/SharpCompute.SourceGenerators.Tests` for the emitted MSL
  and for the diagnostics.

## Diagnostics

Generator diagnostics are numbered `SCG0001` upwards (`SCG9999` is the internal error). A new one
takes the next free number, is declared in
`src/SharpCompute.SourceGenerators/DiagnosticDescriptors.cs` and is listed in
`src/SharpCompute.SourceGenerators/AnalyzerReleases.Unshipped.md`; the build fails if the two
disagree. Numbers are never reused.

## Demos and screenshots

A new feature comes with a demo: a sample, or a ComputeLab page, that runs in a window and also
headless. A new sample has a `scripts/demo-<name>.sh` built on `scripts/_common.sh` and is added to
`scripts/run-demos.sh`.

The README shows every demo. A new or changed demo regenerates its screenshot and thumbnail with
`scripts/make-screenshots.sh <demo>` (and its animation with `scripts/make-gifs.sh <name>`), and
appears in the README's [Demos](README.md#demos) grid. The `ReadmeImage` tests check that every
image exists, has alt text, is opaque and is within its size limit. Don't commit `demo-output/`,
build output or benchmark artifacts.

Timings quoted in a pull request or the README name the hardware and are the median of several runs
on an otherwise idle machine.

## Pull requests

- One topic per pull request, branched from `main`.
- A clear title and a description with sections like the existing pull requests: what and why, the
  API, tests, design decisions (each judgement call with its reason) and limitations.
- Update the README when behaviour, the API or a limitation changes.
- Every pull request is reviewed before it is merged, and merges are squash merges, so the title
  becomes the commit message on `main`.
