## How to read this

- **What a GPU number includes:** one `device.For(...)` call: encoding the dispatch into a new command buffer, `commit`, and `waitUntilCompleted`, plus reading one element of the result back through the shared buffer (to keep the result observable). It is the real synchronous cost of a dispatch as SharpCompute v1 exposes it. The blur is two `For` calls, so it pays that twice.
- **What it excludes:** buffer allocation, uploading inputs and reading back the full result. All buffers are allocated and filled once in `[GlobalSetup]`, and the pipeline is compiled there too, by a warm-up dispatch. The one-off compile cost is measured separately under [First dispatch](#first-dispatch-pipeline-compile).
- **Unified memory, zero copy:** SharpCompute buffers are `MTLStorageModeShared`. CPU and GPU see the same physical memory, so there is no PCIe-style upload or download to amortize. A discrete GPU would add a copy each way; here, "reading the result" is a pointer dereference. That is why moving data is not in the GPU time. It's also why bandwidth-bound kernels (SAXPY) can't beat a multi-threaded CPU by much: both read the same LPDDR5X through the same memory controller.
- **Small workloads:** every dispatch has a fixed floor of roughly 0.1–0.2 ms (command buffer creation, commit, GPU wake-up, completion wait) (measured here: the 65,536 floats SAXPY dispatch, which does almost no work, takes 98.20 µs). A workload the CPU finishes faster than that can't win on the GPU, which is where the crossover above comes from. Zero copy lowers the crossover compared to a discrete GPU (no transfer to amortize), but doesn't remove the floor. Batching several dispatches into one command buffer with a `ComputeContext` amortizes it; see [Batching and async](#batching-and-async).
- **Caches:** at 1M floats SAXPY touches 8 MB, which largely stays in the CPU's on-chip caches between iterations, so the multi-threaded CPU can exceed DRAM bandwidth there. At 16M floats (192 MB of traffic per call) both sides are DRAM-bound.
- **CPU variants** run on managed arrays. *scalar (1 thread)* is a plain loop; *SIMD* uses `TensorPrimitives`, `Vector<T>` or `Vector128<T>` (128-bit NEON, 4 floats); *Parallel.For* spreads rows, chunks or bodies across all cores. The CPU matmul gets Bᵀ (transposed once in setup, not timed); the N-body SIMD variant gets a structure-of-arrays copy (also built once in setup).
- **FP contraction:** Metal fuses `a*b + c` into fma by default, so GPU results match the CPU to rounding, not bit for bit. That's what `--verify` checks.
- **When unified memory helps and when it doesn't:** the zero-copy, batching and async sections below measure it; [`docs/unified-memory.md`](../docs/unified-memory.md) explains which API to use when, and covers one-off measurements outside this suite, such as GPU-private vs shared buffers.

- Each extra dispatch (from K = 1 to K = 100) costs about **100.47 µs** as another `device.For` (a whole submit-and-wait), **1.83 µs** inside one `ComputeContext` and **8.92 µs** as another back-to-back `ForAsync` (still its own command buffer and completion handler). Use a context for many small dispatches; `ForAsync` is for overlapping CPU work with the GPU.
- A device's queue has 64 command buffers. Back-to-back `ForAsync` beyond 64 in flight blocks in `commandBuffer` until one completes, which is part of the larger-K `ForAsync` rows. A pending `ComputeContext` holds none: it encodes when it is executed.
- The two-pass blur saves one submission: 1.64 ms → 1.44 ms (−12 %). The kernels dominate at 4K, so batching two passes is a small win there.
- Overlap: GPU render alone 8.17 ms, CPU analysis alone 25.91 ms (of the same 8 frames). Perfect overlap cannot beat max(GPU, CPU) = 25.91 ms; sync takes 38.22 ms (GPU + CPU = 34.08 ms, plus a submission and wake-up per frame) and double-buffered `ForAsync` 27.84 ms: **1.37×**, 7.5 % above the ideal.

### Image pipeline

Zero-copy data paths. A decoded 3840×2160 RGBA8 image (one `uint` per pixel) blurred (radius 8, separable, clamped) into RGBA8 ready to encode; decoding and encoding are identical for every variant and not timed. *Zero copy* has the decoder write into the buffer's shared memory (`AsSpan`); two kernels read the bytes, blur and write bytes, and the encoder reads the output in place. *Copies in and out* runs the same two kernels on bytes kept in managed arrays, so the difference is the cost of the two 33 MB copies alone. *CPU conversions + copies* is a pipeline on `Float4` arrays: the CPU converts bytes to floats, 133 MB is copied in, Float4 kernels blur, 133 MB is copied out and the CPU converts back. Baseline: the CPU pipeline, Parallel.For over rows with one `Vector4` (one NEON register) per pixel.

## First dispatch (pipeline compile)

A plain `Stopwatch`, not BenchmarkDotNet. Each sample is a fresh process (`--first-dispatch`) that creates the default device and then dispatches the 1920×1080, 512-iteration Mandelbrot. The first dispatch compiles the generated MSL into a pipeline (`newLibraryWithSource` + `newComputePipelineState`) and then runs it. Compile ≈ first − steady. macOS keeps a system-wide Metal shader cache, so these are typically warm-cache compiles; a never-seen shader on a clean cache takes longer.

## Verification (`--verify`)

Run before benchmarking; the script stops if any check fails. Bit-exactness is only expected of single arithmetic ops, so every float result is compared with a relative tolerance of 1e-5 (the bit-exact share is reported as a detail). Mandelbrot compares iteration counts (±1 allowed) against a CPU reference that fuses the same multiply-adds Metal's default FP contraction fuses; against the unfused CPU loop, a fraction of a percent of boundary pixels follow a different chaotic orbit. N-body compares per-body vectors, with the relative error's denominator floored at the RMS magnitude over all bodies.
