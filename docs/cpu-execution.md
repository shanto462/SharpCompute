# CPU execution: ForCpu and ForSplit

The C# of a shader is real code. `ForCpu` runs it on all CPU cores, and `ForSplit` runs part of the
grid on the CPU and the rest on the GPU, in one dispatch.

- [What matches the GPU](#what-matches-the-gpu)

## Running on the CPU

`ForCpu` runs a shader on all CPU cores, with `ThreadIds`, `DispatchSize` and the other built-ins
returning per-thread values, and buffers read and written in place. `ForSplit` runs the leading rows
of the grid on the CPU while the GPU runs the rest, on the same shared buffers, and returns when both
are done:

```csharp
device.ForCpu(width, height, new Blur(source, destination));       // CPU only
device.ForSplit(width, height, new Blur(source, destination));     // adaptive CPU share
device.ForSplit(width, height, new Blur(source, destination), 0.25); // a quarter of the rows on the CPU
device.ForEachSplit(texture, new Gradient(time: 1.5f));            // pixel shaders too
```

`device.ForIndirectCpu` runs an [indirect dispatch](dispatch.md#indirect-dispatch) on the CPU.

`ForCpu` is a correct fallback and a debugging aid rather than a fast CPU path. It is also the way to
find out-of-bounds indexing: the GPU has no bounds checks, while the C# throws
`IndexOutOfRangeException`.

## Splitting between the CPU and the GPU

Both parts of a split see the whole grid (`ThreadIds`, `DispatchSize`, `ThreadIds.Normalized`). Only
split shaders whose threads write their own elements.

Don't expect much from the split. The CPU runs the shader's scalar C#, and the GPU slows down while
every CPU core is busy. So the adaptive mode only splits while that measures faster than the GPU
alone. On the benchmarked workloads it lands between 3 % slower and 9 % faster than GPU-only
([`benchmarks/RESULTS.md`](../benchmarks/RESULTS.md#cpu-execution-and-cpugpu-split), and the table
in [Unified memory](unified-memory.md#splitting-one-dispatch-between-the-cpu-and-the-gpu)).

Split results are not bit-reproducible across calls unless you pass an explicit CPU fraction,
because the CPU and the GPU round floats differently. `device.Prepare<T>(PrepareOptions.IncludeSplit)`
also compiles the pipeline that `ForSplit` runs on the GPU (see
[Precompiled shaders](precompiled-shaders.md#warm-up-with-prepare)).

## What matches the GPU

- Results match the GPU up to floating-point rounding.
- Integer results are identical: conversions from float saturate, shift counts are masked, and
  arithmetic wraps on both, signed and unsigned (see [Integers](shader-language.md#integers)).
- The CPU implementations of `Gpu.*` are bit-for-bit for arithmetic, rounding functions, `sqrt` and
  `fmod`, and within a few ULP for transcendentals. With `[ShaderOptions(FpContract = false)]`,
  arithmetic that uses only `+ - * /` and `Gpu.Sqrt` gives the same bits on both (subnormal results
  aside, which the GPU flushes to zero).
- Both run the shader's expressions in the same order: one whose result would depend on C#'s
  left-to-right evaluation, through a local or through what it (or a helper it calls) writes to a
  buffer, a `[GroupShared]` array or a texture, is build error `SCG0021` (see
  [Evaluation order](shader-language.md#evaluation-order)).
- `checked` arithmetic is build error `SCG0052`: it would throw `OverflowException` under `ForCpu`
  and wrap on the GPU.
- The [conformance suite](#semantics-and-conformance) pins all of this, operator by operator.

## Semantics and conformance

The `tests/SharpCompute.Tests/Conformance` suite runs every operator, conversion and intrinsic family of the
shader language on the GPU and with `ForCpu` over the same edge values (0, ±1, the minimum and
maximum of each type and their neighbours, overflow points, shift counts at and beyond the width
and negative ones, ±0, subnormals, ±∞ and NaNs of both signs) and compares them slot by slot:
`dotnet test --filter Category=Conformance` runs the conformance suites. The shaders are generated by
`tools/gen_conformance.py`, one per family and type. The CPU side is described in the remarks of
[`GraphicsDevice.ForCpu`](../src/SharpCompute/Runtime/GraphicsDevice.Cpu.cs).

- **Exact**, bit for bit: every integer operator, compound assignment, increment and shift of every
  integer type and of the `int`/`uint` vectors (wrapping, promotion and shift masking as in unchecked
  C#), the bool vectors, every conversion between scalar types and between vector types (float to
  integer saturates, NaN gives 0), the integer and bit intrinsics, half arithmetic and the half
  functions that are not transcendental. Any NaN equals any NaN: the GPU writes a positive canonical
  NaN, .NET's has its sign bit set.
- **`System.Math`, `MathF` and `float` statics follow .NET**, which `ForCpu` runs: `Min` and `Max`
  propagate NaN and order `-0` below `+0`, `Math.Clamp(x, lo, hi)` is `x < lo ? lo : x > hi ? hi : x`
  (a NaN `x` stays NaN), `float.Clamp` is `Min(Max(x, lo), hi)` (a NaN bound gives NaN),
  `float.Lerp(a, b, t)` is `fma(a, 1 - t, b * t)`, `MathF.ILogB(NaN)` is `int.MaxValue`, and the
  `%` of two scalar halves gives a zero remainder the sign of the dividend. These go through small
  prelude helpers. `Gpu.Min`, `Max` and `Clamp` are MSL's `fmin`/`fmax` forms instead (a NaN operand
  gives the other operand) and `Gpu.Lerp` is `metal::mix`: they are the fast choice with Metal's
  semantics. In a tight loop of nothing but `Max` and `Min`, `MathF.Max`/`Min` are about 2× slower
  than `Gpu.Max`/`Min` on an Apple M4 Pro.
- **Exact up to subnormal flushing**: an Apple GPU flushes float subnormal operands and results to a
  zero of the same sign (a result that rounds up to the smallest normal from below as well), and
  `ForCpu` does not. Float arithmetic, comparisons, conversions from float and the float functions
  that are not transcendental give `ForCpu`'s result for the operands as they are or with their
  subnormals flushed. `Abs`, `CopySign`, negation and `%` copy a subnormal unflushed; `Min`, `Max`,
  `Clamp` and `Select` compare the flushed operands and return one of them unflushed. Half
  subnormals are kept.
- **Within a tolerance**: the transcendental functions (`Sin`, `Exp`, `Log`, `Pow`, `Atan2` and the
  rest, of `Gpu` and of `MathF`) within 4 float ULP or 1 half ULP, and the composite ones (`Lerp`,
  `Smoothstep`, `Dot`, `Length`, `Normalize`, `Reflect`, `Cross`) as well, except near the subnormal
  range, where an intermediate result can be flushed. `a * b + c` is fused into one fma on the GPU
  (unless `[ShaderOptions(FpContract = false)]`), so it is not compared.
- **Unspecified**, and only checked not to crash: integer division and remainder by zero, and
  `MathF.ReciprocalSqrtEstimate`, whose precision is the CPU's.
- **Where .NET throws**, `ForCpu` throws and the GPU carries on, and the suite pins what it returns:
  `Math.Abs` of the minimum of a signed type is that minimum, `MathF.Sign(NaN)` is 0, `Math.Clamp`
  with `min > max` gives `min` below `min` and `max` otherwise, and `int.MinValue / -1` is
  `int.MinValue` and `int.MinValue % -1` is 0 (the same for `long`).
- **`checked`** arithmetic is refused at build time (`SCG0052`): it would throw on the CPU and wrap
  on the GPU.

## Feature by feature

| Feature | On the CPU | Details |
|---|---|---|
| `[GroupShared]` memory and barriers | One dedicated thread per thread of a threadgroup (at most 1,024), meeting at every barrier, one group after another. Exact, but thousands of times slower than the GPU | [Shared memory](shared-memory.md#on-the-cpu) |
| SIMD-group operations | The 32 lanes of a group run on threads of their own and meet at every operation. Needs uniform control flow; about a quarter of a millisecond per operation and SIMD group | [SIMD groups](simd-groups.md#on-the-cpu) |
| Atomics | `Interlocked` operations; final values match. A shader with atomics on buffer elements is never split | [Atomics](atomics.md#on-the-cpu-and-between-devices) |
| Textures | The same reads, writes and address modes, exact where the GPU rounds | [Textures on the CPU](resources.md#textures-on-the-cpu) |
| Local arrays | Real C# arrays and spans, bounds-checked. `new T[N]` allocates per thread: prefer `stackalloc` | [Local arrays](local-arrays.md#rules) |
| Half precision | Reproduces the GPU's half arithmetic bit for bit, subnormals included | [Half precision](half-precision.md#what-it-computes) |
| Shared code | The same methods, unchanged | [Sharing code](shared-code.md#rules) |
| Matrix units | The lanes meet at every matrix operation and the matrix is storage the group shares; lanes at different calls, different arguments or fewer than 32 lanes are refused | [Matrix units](matrix-units.md#on-the-cpu) |
